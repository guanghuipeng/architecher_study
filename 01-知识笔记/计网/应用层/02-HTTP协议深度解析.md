### 卡片 2.2.1：Web 页面 = 一个 HTML 文件 + N 个对象

```
    你看到的网页：
    ┌──────────────────────────────┐
    │  ┌──────────────────────┐    │
    │  │  Logo 图片            │    │  ← logo.png (一个对象)
    │  └──────────────────────┘    │
    │  ┌──────────────────────┐    │
    │  │  这是正文内容...       │    │  ← index.html (base HTML)
    │  │  ┌────────────────┐  │    │
    │  │  │  广告图片        │  │    │  ← ad.jpg (一个对象)
    │  │  └────────────────┘  │    │
    │  └──────────────────────┘    │
    └──────────────────────────────┘

每个"对象"都有自己的 URL：
  http://www.example.com/images/logo.png
  └─协议─┘└──主机名───┘└────路径────────┘

一个网页 = 1 个 HTML 基础文件 + 引用的 N 个对象(JS/CSS/图片/视频)
每个对象可能放在不同服务器上！
```

### 卡片 2.2.2：HTTP 是无状态协议 —— 这是故意的！

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│  HTTP = Stateless（无状态）                          │
│                                                     │
│  服务器不记得你上次请求了什么                          │
│  每一个 HTTP 请求都是独立的                           │
│                                                     │
│  为什么？                                            │
│    ✅ 服务器简单 —— 不需要维护历史                     │
│    ✅ 崩溃恢复简单 —— 没有状态要恢复                   │
│    ✅ 扩展性好 —— 请求可以到任何一台服务器              │
│                                                     │
│  那购物车怎么办？                                     │
│    → Cookie! (见卡片 2.2.6)                          │
│                                                     │
└─────────────────────────────────────────────────────┘

反面教材：如果 HTTP 是有状态的——

  客户端：         服务器：
  加商品A到购物车    状态: [A]
  加商品B到购物车    状态: [A, B]
  网络断了！断网！    状态: [A, B]  
  重新连接...
  加商品C到购物车    状态: [C]  ← 丢了 A 和 B！
  
状态协议需要处理这种不一致，非常复杂。
HTTP 选择简单：每次请求自己带齐所有信息（比如 Cookie 里存着购物车 ID）
```

### 卡片 2.2.3：非持久 HTTP vs 持久 HTTP（面试必考！）

```
HTTP 1.0: 非持久连接 (Non-persistent)

  客户端                      服务器
    │──── TCP 建立 ─────────────│
    │──── GET index.html ──────►│  ← 1 RTT
    │◄─── index.html ─────────│
    │──── TCP 关闭 ─────────────│
    │                          │
    │──── TCP 建立 ─────────────│  ← 又要重新握手！
    │──── GET logo.png ────────►│
    │◄─── logo.png ───────────│
    │──── TCP 关闭 ─────────────│
    │                          │
    │   ... 重复 10 次 ...      │
    │                          │
  每个对象 = 2RTT + 传输时间
  10 个对象 = 20RTT + 10 × 传输时间  ← 很慢！

══════════════════════════════════════════════════════

HTTP 1.1: 持久连接 (Persistent, keep-alive)

  客户端                      服务器
    │──── TCP 建立 ─────────────│
    │──── GET index.html ──────►│  ← 连接保持打开！
    │◄─── index.html ─────────│
    │──── GET logo.png ────────►│  ← 复用同一连接
    │◄─── logo.png ───────────│
    │──── GET style.css ───────►│
    │◄─── style.css ──────────│
    │──── GET app.js ──────────►│
    │◄─── app.js ─────────────│
    │──── TCP 关闭 ─────────────│  ← 最后才关

  所有对象 ≈ 1RTT + 传输时间  ← 快了一倍！
```

### 卡片 2.2.4：HTTP 请求报文——到底长什么样

```
一个真实的 HTTP GET 请求：

  GET /index.html HTTP/1.1\r\n           ← 请求行 (method sp URL sp version)
  Host: www-net.cs.umass.edu\r\n         ← 首部行开始
  User-Agent: Mozilla/5.0 ...\r\n
  Accept: text/html,application/xhtml+xml\r\n
  Accept-Language: en-us,en;q=0.5\r\n
  Accept-Encoding: gzip,deflate\r\n
  Connection: keep-alive\r\n
  \r\n                                   ← 空行 = 首部结束
  (如果是 POST，这里放 entity body)

  请求行
  ┌────────────────────────┐
  │ method  │  URL  │version│
  │ GET     │ /     │HTTP/1.1│
  │ POST    │/login │HTTP/1.1│
  │ HEAD    │/      │HTTP/1.1│
  │ PUT     │/file  │HTTP/1.1│
  │ DELETE  │/user/1│HTTP/1.1│
  └────────────────────────┘

GET vs POST 的区别：
  GET:  参数在 URL 里  (/?q=hello&page=2)
        ⚠ 有长度限制，会出现在浏览器历史、服务器日志
  
  POST: 参数在 body 里
        ✅ 无长度限制，不暴露在 URL，适合敏感数据

HEAD: 只要响应头，不要响应体（检查资源是否更新）
PUT:  上传文件到服务器（覆盖已有）
DELETE: 删除资源
```

### 卡片 2.2.5：HTTP 响应报文 + 状态码记忆法

```
一个真实的 HTTP 响应：

  HTTP/1.1 200 OK\r\n                    ← 状态行
  Date: Tue, 08 Sep 2020 00:53:20 GMT\r\n
  Server: Apache/2.4.6 (CentOS)\r\n
  Last-Modified: Tue, 01 Mar 2016 18:57:50 GMT\r\n
  Content-Length: 2651\r\n
  Content-Type: text/html; charset=UTF-8\r\n
  \r\n                                   ← 空行 = 头部结束
  <html><body>...</body></html>         ← 响应体（数据）

═══════════════════════════════════════════════════════

状态码记忆法 —— 按首个数字分组：

  1xx = 信息
  2xx = 成功    200 OK ✓  201 Created
  3xx = 重定向  301 永久搬家  302 临时搬家  304 没变化(缓存)
  4xx = 客户端错  400 你请求写错了  401 未认证  403 禁止访问  404 找不到
  5xx = 服务器错  500 服务器崩了  502 网关错  503 服务不可用

记忆口诀："2成3转4你错5我错"
```

### 卡片 2.2.6：Cookie —— 让无状态的 HTTP 有「记忆」

```
  Cookie 是怎么工作的？

  第1步：首次访问
    客户端 ──── GET / ─────────► 服务器
    客户端 ◄── 200 OK ───────── 服务器
             Set-Cookie: 1678    ← 服务器说"你的编号是1678"
    
  第2步：浏览器存起来
    ┌─────────────────┐
    │ Cookie 文件      │
    │ amazon: 1678    │  ← 浏览器自动保存
    └─────────────────┘

  第3步：下次请求自动带上
    客户端 ──── GET /cart ──────► 服务器
             Cookie: 1678        ← 浏览器自动附上
    客户端 ◄── 200 OK ───────── 服务器
             "你好1678，你的购物车有3件商品"

  四个组件：
    ① HTTP 响应头里的 Set-Cookie
    ② HTTP 请求头里的 Cookie
    ③ 浏览器端的 Cookie 文件
    ④ 网站后端的数据库 (存 Cookie → 用户数据的映射)

  ⚠ 隐私问题：
    第三方 Cookie = 广告公司跨网站追踪你
    你在 A 站搜了"袜子"→ 广告商知道 → 在 B 站给你推袜子广告
    (详见补充幻灯片 ch2_supplemental)

  Firefox/Safari 默认禁用第三方 Cookie
  Chrome 在 2023 年也开始禁用
```

### 卡片 2.2.7：Web 缓存 (Proxy) —— 为什么你的网页加载快？

```
没有缓存时：
  客户端 A ──────────────────────────► 源服务器
            ◄─────── 2秒 ─────────────  (美国)
  客户端 B ──────────────────────────► 源服务器
            ◄─────── 2秒 ─────────────  

有缓存时：
  客户端 A ────► Web缓存 ────► 源服务器
            ◄─1ms─┘  ◄──2s──┘   存一份！
  客户端 B ────► Web缓存 (命中!)
            ◄─1ms─┘             不用去美国了！

═══════════════════════════════════════════════════════

缓存命中率 40% 的效果（教科书案例）：

  接入链路利用率：0.97 → 0.58（从堵塞到轻松）
  平均延迟：     分钟级 → 1.2秒
  
  结论：40% 命中率的便宜缓存 > 100 倍贵的接入链路！
  
═══════════════════════════════════════════════════════

条件 GET (Conditional GET)：缓存有旧版本，怎么知道要不要更新？

  客户端 ──── GET /logo.png ─────────────────────► 服务器
              If-Modified-Since: Mon, 1 Jan 2024
  
  → 没改：◄── 304 Not Modified ────── (不发数据，省带宽!)
  → 改了：◄── 200 OK + 新图片数据
```

### 卡片 2.2.8：HTTP/1.1 的队头阻塞问题 🔑

```
  HTTP/1.1 的管道化 (Pipelining)：

  客户端一次性发送：GET O₁, GET O₂, GET O₃, GET O₄
  服务器按顺序返回：O₁ → O₂ → O₃ → O₄ (FCFS 调度)

  问题来了：
  ┌─────────────────────────────────────────────┐
  │  O₁ 是个大视频 (100MB)                       │
  │  O₂ 是个小图标 (5KB)                         │
  │  O₃ 是个 CSS (10KB)                          │
  │  O₄ 是个 JS  (20KB)                          │
  │                                             │
  │  O₂ O₃ O₄ 虽然很小，但必须排队等 O₁ 传完！    │
  │  → 这就是 Head-of-Line (HOL) Blocking         │
  └─────────────────────────────────────────────┘
```

### 卡片 2.2.9：HTTP/2 如何解决队头阻塞

```
  HTTP/2 的解决方案：把对象切割成帧，交错传输

  HTTP/1.1 (FCFS):
  ┌─O₁─┬─O₁─┬─O₁─┬─O₁─┬─O₂─┬─O₃─┬─O₄─┐
  │   大视频还在传输...小文件全在等...│
  └────┴────┴────┴────┴────┴────┴────┘

  HTTP/2 (帧交错):
  ┌─O₂─┬─O₃─┬─O₁─┬─O₄─┬─O₁─┬─O₃─┬─O₁─┬─O₄─┐
  │小图标│CSS │视频│ JS │视频│CSS │视频│ JS │
  └─────┴────┴───┴────┴───┴────┴───┴────┘
    小对象快速加载完成！大对象稍慢但不阻塞别人

  HTTP/2 新增能力：
    ✅ 帧交错 → 缓解 HOL 阻塞
    ✅ 服务器推送 (Server Push): 客户端还没要 CSS，服务器主动发
    ✅ 头部压缩 (HPACK): 减少重复头部传输
    ✅ 客户端可指定对象优先级

  但是 HTTP/2 还在 TCP 上 → TCP 丢包时所有帧都受影响 → HTTP/3 来了
```

### 卡片 2.2.10：HTTP 版本演进路线图

```
  HTTP/0.9  (1991)  只支持 GET，没有头部
     ↓
  HTTP/1.0  (1996)  增加了 POST/HEAD、状态码、头部
     ↓              缺点：每个对象新开一个 TCP 连接
  HTTP/1.1  (1997)  持久连接、管道化、Host 头、缓存控制
     ↓              缺点：队头阻塞 (HOL Blocking)
  HTTP/2    (2015)  二进制分帧、多路复用、服务器推送
     ↓              缺点：TCP 丢包阻塞所有流
  HTTP/3    (2020+) 基于 QUIC (UDP)、0-RTT 握手
                    每个对象独立的错误和拥塞控制
                    彻底解决 TCP 队头阻塞！

  当前主流：HTTP/1.1 和 HTTP/2 共存
  未来趋势：HTTP/3 逐渐普及

  HTTP/3 的核心变化：
  ┌──────────────────────────────┐
  │  HTTP/1.1 → HTTP/2: 改应用层 │
  │  HTTP/2  → HTTP/3: 改传输层！│
  │  从 TCP 换成了 QUIC/UDP       │
  └──────────────────────────────┘
```

## 🔬 动手实验

### 实验 1：手写 HTTP 请求（最直观的体验）

打开终端，输入：

```bash
# Windows 用这个（PowerShell）:
# 先安装 netcat 或直接用 telnet
telnet gaia.cs.umass.edu 80

# 连接成功后，手动输入（注意大小写）：
GET /kurose_ross/interactive/index.php HTTP/1.1
Host: gaia.cs.umass.edu

# 敲两次回车！你会看到服务器返回完整的 HTTP 响应
```

### 实验 2：用浏览器 F12 看 HTTP

```
1. 打开浏览器，按 F12
2. 切换到 Network 标签
3. 访问任意网页 (比如 www.bilibili.com)
4. 点第一个请求，看：
   - Request Headers (你发了什么)
   - Response Headers (服务器回了什么)
   - Status Code (200? 304? 404?)
   - Timing (DNS 用了多久？TCP 握手多久？)
```

### 实验 3：用 curl 查看完整 HTTP 交互

```bash
# 查看完整的请求和响应头
curl -v http://gaia.cs.umass.edu/kurose_ross/interactive/

# 只看响应头
curl -I http://gaia.cs.umass.edu/kurose_ross/interactive/

# 用条件 GET 测试缓存
curl -I -H "If-Modified-Since: Tue, 01 Mar 2024 18:57:50 GMT" \
  http://gaia.cs.umass.edu/kurose_ross/interactive/
```
