### 卡片 2.3.1：电子邮件系统的三组件

```
  ┌──────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────┐
  │  用户代理 │     │   邮件服务器   │     │   邮件服务器   │     │  用户代理 │
  │  (UA)    │     │              │     │              │     │  (UA)    │
  │          │────►│  消息队列     │────►│  邮箱        │────►│          │
  │  Outlook │ SMTP│   (待发送)    │ SMTP│  (待接收)    │IMAP │  Outlook │
  │  网页邮箱 │     │              │     │              │HTTP │  网页邮箱 │
  └──────────┘     └──────────────┘     └──────────────┘     └──────────┘
     Alice              Alice 的           Bob 的               Bob
                        邮件服务器         邮件服务器

三个关键组件：
  ① 用户代理 (User Agent): Outlook, Thunderbird, Gmail App, iPhone Mail
  ② 邮件服务器: 存邮件、转发邮件
     - 邮箱 (mailbox): 收到的邮件存在这里
     - 消息队列 (message queue): 要发出去的邮件排队
  ③ SMTP 协议: 邮件服务器之间的通信语言
```

### 卡片 2.3.2：SMTP —— 推 (Push) 协议

```
  一个真实的 SMTP 对话（服务器之间）：

  S: 220 hamburger.edu                    ← 服务器就绪
  C: HELO crepes.fr                       ← 客户端打招呼
  S: 250 Hello crepes.fr, pleased to meet you
  C: MAIL FROM: <alice@crepes.fr>        ← 发件人
  S: 250 alice@crepes.fr... Sender ok
  C: RCPT TO: <bob@hamburger.edu>        ← 收件人
  S: 250 bob@hamburger.edu... Recipient ok
  C: DATA                                 ← 开始传邮件内容
  S: 354 Enter mail, end with "." on a line by itself
  C: Do you like ketchup?                ← 邮件正文
  C: How about pickles?
  C: .                                    ← 一个点 = 结束
  S: 250 Message accepted for delivery
  C: QUIT                                 ← 关闭连接
  S: 221 hamburger.edu closing connection

═══════════════════════════════════════════════════════

SMTP 特点：
  ✅ 持久连接（不会发一封关一次）
  ✅ 要求 7-bit ASCII（不能直接支持中文/图片/附件 → 用 MIME 编码）
  ✅ 用 CRLF.CRLF 判断消息结束
  ✅ 命令/响应模式（类似 HTTP）

HTTP vs SMTP 对比：
  ┌────────────┬─────────────────┬──────────────────┐
  │            │     HTTP        │      SMTP        │
  ├────────────┼─────────────────┼──────────────────┤
  │  方向      │  Pull（客户端拉）│  Push（发送方推）  │
  │  对象      │  每个对象独立响应 │  多个对象打包发送  │
  │  编码      │  不限（二进制OK）│  7-bit ASCII     │
  │  状态码    │  有             │  有              │
  └────────────┴─────────────────┴──────────────────┘
```

### 卡片 2.3.3：收邮件 —— IMAP vs POP3 vs HTTP

```
  Alice 发邮件：
  ┌────┐  SMTP  ┌──────────┐  SMTP  ┌──────────┐
  │ UA │ ─────► │Alice 的   │ ─────► │ Bob 的    │
  └────┘        │邮件服务器  │        │邮件服务器  │
                └──────────┘        └─────┬────┘
                                          │
  Bob 收邮件：（三种方式）                   │
  ┌────────────────────────────────────────┘
  │
  ├── IMAP (端口 143)
  │   邮件一直留在服务器上
  │   支持文件夹、已读/未读状态同步
  │   手机/电脑/网页 看到的是同一份
  │   ✅ 多设备同步 → 现代标配
  │
  ├── POP3 (端口 110)
  │   下载到本地，完成后删除服务器上的
  │   换个设备就看不到了
  │   ❌ 基本淘汰，除非特殊安全需求
  │
  └── HTTP (Gmail/Hotmail 的 Web 界面)
      浏览器 ↔ Gmail 服务器：用 HTTP
      Gmail 服务器 ↔ 其他邮件服务器：用 SMTP
      Gmail 服务器 ↔ 你的手机 App：用 IMAP
```

### 卡片 2.3.4：DNS 是什么？为什么不能集中化？

```
  DNS = 互联网的电话簿
  ┌──────────────────┐          ┌──────────────────┐
  │ www.bilibili.com │ ──DNS──►│ 120.240.xxx.xxx  │
  │ (人类记得住)      │          │ (机器用这个通信)   │
  └──────────────────┘          └──────────────────┘

Q: 为什么不搞一个中心化的 DNS 服务器？
  全世界所有域名 → 一台超级服务器 → 搞定？

A: 四个致命问题：
  ❌ 单点故障      → 这台机器挂了，整个互联网瘫痪
  ❌ 流量太大      → Comcast 一家 DNS 每天处理 6000 亿次查询
  ❌ 距离太远      → 北京的请求跑到纽约去查，延迟感人
  ❌ 维护不可能    → 上亿个域名，谁管得过来？

DNS 的设计答案：分布式、层级化数据库

  每天处理：数万亿次查询
  记录数：  约 10 亿条（但每条很简单）
  读多写少：  查询 >> 更新
  几乎每次互联网交互都先触发一次 DNS 查询
```

### 卡片 2.3.5：DNS 层级结构 —— 互联网最漂亮的分布式设计

```
                     ┌─────────────────────┐
                     │    Root DNS Servers  │  13 个逻辑服务器
                     │    (根域名服务器)      │  每个被复制数百次
                     └──────┬──────┬───────┘
                            │      │
              ┌─────────────┘      └─────────────┐
              ▼                                   ▼
   ┌──────────────────┐                ┌──────────────────┐
   │ .com TLD Server  │                │ .org TLD Server  │
   │ (顶级域名服务器)   │                │                  │
   │ 维护所有 .com 域名 │                │ 维护所有 .org 域名 │
   └────────┬─────────┘                └──────────────────┘
            │
            ▼
   ┌──────────────────┐
   │ bilibili.com     │  权威 DNS 服务器 (Authoritative)
   │ (Authoritative)  │  这里存着 www.bilibili.com → IP 的
   │                  │  最终答案
   └──────────────────┘
   │ amazon.com       │
   │ (Authoritative)  │
   └──────────────────┘

  还有一层：本地 DNS 服务器 (Local DNS Server)
  ┌─────────────────────────────────────────────┐
  │  你的电脑 → 本地 DNS (ISP 提供) → 帮你一级级查  │
  │  不属于层级结构，但是每个 DNS 查询的起点        │
  └─────────────────────────────────────────────┘
```

### 卡片 2.3.6：DNS 解析的两种方式 —— 迭代 vs 递归

```
迭代查询 (实际最常用):

  你的电脑                          本地DNS
    │                                 │
    │──① 帮我查 gaia.cs.umass.edu ──►│
    │                                 │──② 问根DNS──►
    │                                 │◄── "去问 .edu TLD" ──
    │                                 │──③ 问 .edu TLD ──►
    │                                 │◄── "去问 umass.edu 权威" ──
    │                                 │──④ 问 umass.edu ──►
    │                                 │◄── IP: 128.119.245.12 ──
    │◄──────⑤ IP = 128.119.245.12 ──│
    │                                 │
  关键：本地DNS 一台一台地问，每台说"我不知道，但你去问XXX"
  你的电脑只发了一次请求！

═══════════════════════════════════════════════════════

递归查询 (理论上):

  你的电脑 ────①──► 本地DNS ────②──► 根DNS ────③──► .edu TLD
       ◄──⑥──         ◄──⑤──         ◄──④──
  
  每一级都要替下一级去查，压力集中在上层！
  实际上只在「你的电脑→本地DNS」这段可能用递归
```

### 卡片 2.3.7：DNS 缓存 —— 为什么第二次查就快了

```
  第一次查 bilibili.com：
    本地DNS → 根 → .com TLD → bilibili.com 权威
    时间：可能几百 ms

  第二次查 bilibili.com：
    本地DNS 直接返回缓存的结果
    时间：< 1ms

  缓存机制：
    ✅ 任何 DNS 服务器学到一条映射后，都会缓存
    ✅ 缓存有时效 (TTL: Time To Live)，过期就删
    ✅ TLD 服务器的地址通常被缓存在本地 DNS 中（连根都省了）

  ⚠ 风险：缓存的可能是过期的
    如果 bilibili 换了 IP，这个更换要等各地 DNS 缓存过期
    才能传遍整个互联网 → DNS 是"尽力而为"的名字解析
```

### 卡片 2.3.8：DNS 记录类型 —— RR (Resource Record)

```
  每条 DNS 记录的格式：(Name, Value, Type, TTL)

  ┌──────────┬──────────────────────────────────────┐
  │  Type    │  含义与示例                           │
  ├──────────┼──────────────────────────────────────┤
  │  A       │  Name=主机名, Value=IP 地址            │
  │          │  (gaia.cs.umass.edu, 128.119.245.12, A)│
  ├──────────┼──────────────────────────────────────┤
  │  NS      │  Name=域名, Value=权威DNS 的主机名      │
  │          │  (umass.edu, dns.umass.edu, NS)      │
  ├──────────┼──────────────────────────────────────┤
  │  CNAME   │  Name=别名, Value=真实名(规范名)        │
  │          │  (www.ibm.com, servereast.backup2.ibm.com, CNAME)│
  ├──────────┼──────────────────────────────────────┤
  │  MX      │  Name=域名, Value=邮件服务器名          │
  │          │  (umass.edu, mail.umass.edu, MX)     │
  └──────────┴──────────────────────────────────────┘

  实际使用场景：
    A:    查 www.google.com → 142.250.xxx.xxx
    NS:   .com TLD 说 "umass.edu 的权威DNS是 ns1.umass.edu"
    CNAME: www.baidu.com 其实是 www.a.shifen.com 的别名
    MX:   发邮件给 @gmail.com → MX 指向 gmail-smtp-in.l.google.com
```

### 卡片 2.3.9：DNS 协议消息 —— 查询和响应格式一致

```
  DNS 查询和响应使用完全相同的报文格式：

  ┌──────────────────┬──────────────────┐
  │   identification  │      flags       │  2字节 × 2
  ├──────────────────┼──────────────────┤
  │   # questions    │   # answer RRs   │  2字节 × 2
  ├──────────────────┼──────────────────┤
  │   # authority RRs│  # additional RRs│  2字节 × 2
  ├──────────────────┴──────────────────┤
  │   questions (查询的问题)              │  可变长度
  ├─────────────────────────────────────┤
  │   answers (回答的 RR)                │  可变长度
  ├─────────────────────────────────────┤
  │   authority (权威服务器的信息)        │  可变长度
  ├─────────────────────────────────────┤
  │   additional info (附加有用的信息)    │  可变长度
  └─────────────────────────────────────┘

  identification: 查询设置一个 #，响应返回相同的 #
                  客户端用这个 # 匹配查询和响应
  
  DNS 使用 UDP (端口 53)：
    普通查询用 UDP —— 快速，查询/响应一般不超过 512 字节
    区域传输用 TCP —— 数据量大，需要可靠传输
```

### 卡片 2.3.10：DNS 安全

```
  DNS 面临的安全威胁：

  ① DDoS 攻击
     轰炸根服务器 → 历史上通过流量过滤 + 本地缓存挡住
     轰炸 TLD 服务器 → 更危险（根被绕过了）
  
  ② DNS 欺骗 (Spoofing)
     攻击者拦截 DNS 查询，返回假的 IP 地址
     你的浏览器被导向钓鱼网站，地址栏里还是 www.icbc.com.cn

  ③ DNS 缓存投毒 (Cache Poisoning)
     攻击者让 DNS 服务器缓存一条假的记录
     之后所有查询该域名的人都会被导到假地址

  防御：DNSSEC (RFC 4033)
    提供认证和消息完整性
    用数字签名验证 DNS 响应没有被篡改
```

## 🔬 动手实验

### 实验 1：手动 DNS 查询

```bash
# Windows
nslookup www.bilibili.com
nslookup -type=MX gmail.com          # 查邮件服务器
nslookup -type=NS umass.edu          # 查权威 DNS

# Linux/Mac
dig www.bilibili.com
dig www.bilibili.com +trace          # 追踪完整解析过程（超有教育意义！）
dig -t MX gmail.com                  # 查邮件服务器记录
```

### 实验 2：SMTP 对话（只读体验）

```bash
# 连接到 Gmail 的 SMTP 服务器，看看它怎么打招呼
# Windows 用 ncat (nmap 自带)
ncat -v gmail-smtp-in.l.google.com 25

# 你会看到：220 ... ESMTP ...  ← 服务器在跟你打招呼！
# 按 Ctrl+C 退出（我们只是看看，不真的发邮件）
```

### 实验 3：追踪 DNS 解析全过程

```bash
# 最有教育意义的命令——看到每一级 DNS 查询！
dig +trace www.umass.edu

# 你会看到：
# ① 根服务器返回 .edu TLD 的地址
# ② .edu TLD 返回 umass.edu 的权威 DNS
# ③ umass.edu 权威 DNS 返回最终的 A 记录
```
