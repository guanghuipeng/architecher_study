### 卡片 2.6.1：视频 = 压缩 + 传输

```
  原始视频有多大？
    1920×1080 分辨率, 24帧/秒, 24位色彩
    = 1920 × 1080 × 24bit × 24fps
    = 1.19 Gbps  ← 不压缩根本传不了

  压缩两大法宝：

  ① 空间冗余 (Spatial Coding) —— 同一帧内压缩
     ┌────────────────────────┐
     │████████████████████████│  ← 这一大片都是同色紫色
     │████████████████████████│     不需要存 100 个像素值
     │████████████████████████│     只需存：颜色=紫，个数=100
     └────────────────────────┘

  ② 时间冗余 (Temporal Coding) —— 帧之间压缩
     Frame i:   ┌──────────────┐
                │  🏃    🌳    │
                └──────────────┘
     Frame i+1: ┌──────────────┐
                │   🏃   🌳    │  ← 只有人动了一点，树没变
                └──────────────┘
     只传"人的新位置"，背景复用 Frame i

  编码格式的进化：
    MPEG-1: 1.5 Mbps  (VCD 时代)
    MPEG-2: 3-6 Mbps  (DVD 时代)
    MPEG-4: 64Kbps-12Mbps  (互联网时代)
    H.264/H.265: 更高压缩比 (当代主流)

  CBR (恒定码率) vs VBR (可变码率):
    静态画面用低码率，动作场面用高码率 → VBR 更高效
```

### 卡片 2.6.2：流媒体播放的挑战 —— 抖动 (Jitter)

```
  理想情况（网络延迟恒定）：
  
  发送端:  ████████████████████████  (30帧/秒均匀发送)
  接收端:  ████████████████████████  (30帧/秒均匀播放)
           ↑ 刚好匹配，完美！

  现实情况（网络延迟变化 = Jitter）：
  
  发送端:  ████████████████████████  (均匀发送)
  网络:    ██ ███ █ ████ ██ █████ █  (包到达时间不均匀!)
  接收端:  ██   ███  █  ████   ██    (时快时慢 → 卡顿!)

  解决方案：客户端缓冲区 (Playout Buffer)

  接收端先缓冲几秒再开始播放：
  
  网络:    ██ ███ █ ████ ██ █████ █  (到达不均匀)
  缓冲:    ████████████████████████  (但缓冲吸收了这个波动)
  播放:    ████████████████████████  (平滑输出!)
  
  ⚠ 代价：多了几秒初始延迟
    你点开 B 站视频，为什么要等 2-3 秒才开始播？→ 就在填这个缓冲区
```

### 卡片 2.6.3：DASH —— 聪明的自适应码率

```
  DASH = Dynamic Adaptive Streaming over HTTP

  ┌─────────────────────────────────────────────────┐
  │              服务器端                             │
  │                                                 │
  │  视频被切成多个 chunk (每个 2-10 秒)              │
  │                                                 │
  │  chunk1.mp4  →  480p版  720p版  1080p版  4K版   │
  │  chunk2.mp4  →  480p版  720p版  1080p版  4K版   │
  │  chunk3.mp4  →  480p版  720p版  1080p版  4K版   │
  │  ...                                            │
  │                                                 │
  │  manifest.mpd ← 列出所有 chunk 的 URL            │
  └──────────────────────┬──────────────────────────┘
                         │
                         ▼
  ┌─────────────────────────────────────────────────┐
  │              客户端（智能决策！）                  │
  │                                                 │
  │  ① 实时估算带宽："我现在有 5Mbps"                  │
  │  ② 选码率：5Mbps → 能看 720p，选 720p chunk     │
  │  ③ 决定时机：缓冲区快空了 → 赶紧要下一个 chunk    │
  │  ④ 决定来源：A 服务器慢 → 换 B 服务器            │
  │                                                 │
  │  效果：                                           │
  │  网好 → 自动切 1080p                              │
  │  网差 → 自动降 480p（不卡）                        │
  │  用户完全无感知！                                  │
  └─────────────────────────────────────────────────┘

  智能在哪里？
    ✅ 客户端决定（不是服务器）→ 客户端最了解自己的网络状况
    ✅ 每个 chunk 可以选不同的码率 → 实时适应网络变化
    ✅ 可以从不同的 CDN 节点拉 chunk → 避开拥堵
```

### 卡片 2.6.4：CDN —— 为什么 B 站视频秒开？

```
  问题：一部热门番剧，同时 100 万人在看，怎么解决？

  方案1：超级服务器（❌ 不 work）
    ┌─────────┐
    │ Mega Svr│ ← 100 万用户全连这一台
    └────┬────┘     单点故障、网络拥堵、远距离延迟
    ┌────┴──────────────┐
    ▼    ▼    ▼    ▼    ▼  ← 所有用户
    这个方案不扩展！

  方案2：CDN（✅ 实际方案）

              ┌─────────────────────┐
              │     源服务器 (Origin) │  存着完整视频库
              └─────────┬───────────┘
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
  ┌──────────┐    ┌──────────┐    ┌──────────┐
  │ CDN 节点 │    │ CDN 节点 │    │ CDN 节点 │  ← 存热门视频副本
  │  (北京)  │    │  (上海)  │    │  (广州)  │
  └────┬─────┘    └────┬─────┘    └────┬─────┘
       ▼               ▼               ▼
    北京用户         上海用户         广州用户
    (延迟 5ms)      (延迟 5ms)      (延迟 5ms)

  两种部署策略：
    ① Enter Deep: 把 CDN 服务器推进到接入网内部
       比如 Akamai: 24万+ 服务器部署在 120+ 国家
       离用户最近，延迟最低，但管理复杂
    
    ② Bring Home: 在关键 PoP 点放大型集群（几十个节点）
       比如 Limelight
       节点少但每个能力强

  OTT (Over The Top) 挑战：
    内容放在哪个 CDN 节点？→ 热门内容推到边缘
    用户从哪个节点拉？→ DNS 就近解析
    选什么码率？→ DASH 客户端自适应
```

### 卡片 2.6.5：TCP Socket 编程 —— Python 版（与 C++ 对照）

```python
# ============ TCP Server ============
from socket import *

serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)  # ← 创建 socket
serverSocket.bind(('', serverPort))           # ← 绑定到所有网卡
serverSocket.listen(1)                        # ← 开始监听
print('Server ready...')

while True:
    # accept() 阻塞等待，返回新 socket 专门服务这个客户端
    connectionSocket, addr = serverSocket.accept()
    
    # 从这个客户端收数据
    sentence = connectionSocket.recv(1024).decode()
    
    # 处理（这里是大写转换）
    capitalizedSentence = sentence.upper()
    
    # 发回去
    connectionSocket.send(capitalizedSentence.encode())
    
    # 关闭和这个客户端的连接
    connectionSocket.close()
    # 注意：serverSocket 没关！继续 accept 下一个客户端
```

**对应 C++ 代码（你写过的）：**

```cpp
// 同样的逻辑，C++ 版
int sockfd = socket(AF_INET, SOCK_STREAM, 0);    // socket()
bind(sockfd, (sockaddr*)&addr, sizeof(addr));     // bind()
listen(sockfd, backlog);                          // listen()
while (true) {
    int clientfd = accept(sockfd, ...);           // accept() 阻塞等待
    recv(clientfd, buf, len, 0);                  // 收数据
    // ...处理...
    send(clientfd, buf, len, 0);                  // 发数据
    close(clientfd);                              // 关客户端连接
}
```

**关键差异——Python vs C++：**

| | Python | C++ |
|---|---|---|
| 创建 socket | `socket(AF_INET, SOCK_STREAM)` | `socket(AF_INET, SOCK_STREAM, 0)` |
| 错误处理 | 抛异常 | 返回值检查 (`== -1`) |
| 编码 | `send("hello".encode())` | `send(fd, "hello", 5, 0)` |
| 复杂场景 | 适合原型/教学 | 适合生产环境 |

### 卡片 2.6.6：TCP vs UDP —— 代码层面怎么选

```
  TCP (SOCK_STREAM):
    客户端必须 connect()
    服务端必须 listen() + accept()
    用 send()/recv() 收发 → 字节流，没有边界
    ✅ 可靠 → 一次连接建立后，双方像在打电话
    ❌ 开销大 → 三次握手 + 连接状态

  UDP (SOCK_DGRAM):
    不需要 connect()（或 connect 只设默认地址）
    不需要 listen() / accept()
    用 sendto()/recvfrom() 收发 → 每个包独立，有边界
    每次 sendto 都要指定目标地址
    每次 recvfrom 都要接收对方地址
    ✅ 轻量 → 像寄明信片，每张独立
    ❌ 不可靠 → 明信片可能寄丢、可能乱序到达


  技术选型速查表：
  ┌─────────────────────┬───────┬───────┐
  │      场景           │  TCP  │  UDP  │
  ├─────────────────────┼───────┼───────┤
  │ 文件传输/HTTP       │  ✅   │       │
  │ 数据库连接           │  ✅   │       │
  │ 实时语音/视频通话    │       │  ✅   │
  │ 在线游戏（FPS/MOBA） │       │  ✅   │
  │ DNS 查询            │       │  ✅   │
  │ IoT 传感器数据       │       │  ✅   │
  │ 视频直播             │       │  ✅   │
  │ 远程登录 (SSH)      │  ✅   │       │
  │ 即时消息 (微信)      │  ✅   │       │
  └─────────────────────┴───────┴───────┘

  混合场景（实际常见）：
    游戏：UDP 传实时位置 + TCP 传聊天/交易（保证可靠）
    视频会议：UDP 传音视频 + TCP 传共享屏幕/文件
```

### 卡片 2.6.7：TCP 服务端如何处理多个客户端？

```
  问题：一个服务器怎么同时服务 10000 个客户端？

  ┌─────────────────────────────────────────────────┐
  │  方案1：多进程/多线程                             │
  │                                                 │
  │  while True:                                    │
  │      conn = accept()                            │
  │      fork() / new thread → 处理这个客户端        │
  │                                                 │
  │  ✅ 编程简单（每个连接一个线程）                   │
  │  ❌ 10000 连接 = 10000 线程 = 上下文切换灾难       │
  └─────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────┐
  │  方案2：select / poll                            │
  │                                                 │
  │  把所有的 socket fd 交给内核                      │
  │  内核告诉你"哪些 fd 有数据可读"                   │
  │                                                 │
  │  ✅ 不需要一个连接一个线程                          │
  │  ❌ 还是要遍历所有 fd (O(n))                      │
  │  ❌ select 默认最多 1024 个 fd                    │
  └─────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────┐
  │  方案3：epoll (Linux) / kqueue (Mac) / IOCP (Win)│
  │                                                 │
  │  事件驱动！内核主动通知就绪的 fd                   │
  │  不需要遍历，O(1) 获取事件                         │
  │                                                 │
  │  ✅ 支持海量并发（C10K → C100K 问题）             │
  │  ✅ 只有活跃的连接才消耗 CPU                       │
  │  ✅ 你的 Qt 项目在 Linux 下底层就是 epoll          │
  └─────────────────────────────────────────────────┘

  这三个就是你卡片 Q25 讲的 select/poll/epoll 对比！
```
