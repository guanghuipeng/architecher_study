### 卡片 2.1.1：创建网络应用时，你写代码跑在哪里？

```
  ┌──────────────────────┐       ┌──────────────────────┐
  │   终端系统 A          │       │   终端系统 B          │
  │  ┌────────────────┐  │       │  ┌────────────────┐  │
  │  │  你的 App 代码  │  │       │  │  Server 代码    │  │
  │  └───────┬────────┘  │       │  └───────┬────────┘  │
  │          │           │       │          │           │
  └──────────┼───────────┘       └──────────┼───────────┘
             │                              │
        ┌────┴──────────────────────────────┴────┐
        │         网络核心 (路由器/交换机)          │
        │         你不写这里的代码                   │
        │         这里的设备不跑用户应用             │
        └─────────────────────────────────────────┘

关键洞察：应用跑在边缘 → 快速开发、快速传播
网络核心设备不懂你的 HTTP/邮件/视频，它们只管转发数据包
```

### 卡片 2.1.2：Client-Server vs P2P 架构

```
┌─────────────────────────┬──────────────────────────┐
│     Client-Server       │        P2P               │
├─────────────────────────┼──────────────────────────┤
│                         │                          │
│   ┌─────┐               │   ┌──┐     ┌──┐         │
│   │Server│ ← 永远在线    │   │P1│←───→│P2│         │
│   └──┬─┬─┘              │   └┬─┘     └┬─┘         │
│      │  │               │    │    ┌───┘            │
│  ┌───┘  └───┐           │    │    │                │
│  ▼          ▼           │  ┌─▼────▼──┐            │
│ ┌───┐     ┌───┐         │  │   P3    │            │
│ │C1 │     │C2 │         │  └─────────┘            │
│ └───┘     └───┘         │                          │
│ Client 之间不直接通信     │  Peer 之间直接通信        │
│                         │                          │
│ 扩展性: 靠加服务器(花钱)  │  扩展性: 自扩展(新peer   │
│                         │   既消费也提供资源)        │
│ 管理: 简单              │  管理: 复杂              │
│ 例子: HTTP/SMTP/FTP     │  例子: BitTorrent/区块链  │
└─────────────────────────┴──────────────────────────┘

❓ 思考：为什么支付宝不用 P2P？
  → 金融交易必须可靠，中心服务器负责记账和一致性保证。
     P2P 的 peer 随时下线会导致交易丢失。
```

### 卡片 2.1.3：Socket = 应用进程的「门」

```
                             这是最重要的心智模型

    你的进程                              对方的进程
    ┌──────────┐                         ┌──────────┐
    │  App     │                         │  App     │
    │  把消息   │                         │  把消息   │
    │  推进去   │                         │  取出来   │
    └────┬─────┘                         └────┬─────┘
         │  Socket                           │  Socket
    ┌────┴───────────────────────────────────┴─────┐
    │                                             │
    │          ↓ 传输层 (TCP/UDP)                  │
    │          ↓ 网络层 (IP)                       │
    │          ↓ 链路层                            │
    │          ↓ 物理层                            │
    │                                             │
    │   门后面的东西 = OS 管 = 你不管               │
    └─────────────────────────────────────────────┘

进程地址 = IP地址 + 端口号

    128.119.245.12  :  80
    └──────┬──────┘    └┬─┘
       找到主机        找到这个主机上的具体进程

类比：寄快递
  IP地址 = 办公楼地址（定位到建筑）
  端口号 = 房间号（定位到具体办公室里的某个人）
```

### 卡片 2.1.4：应用层协议定义了哪四件事？

```
┌────────────────────────────────────────────────┐
│  ① 消息类型 ──→ 请求? 响应? 通知?               │
│     e.g., HTTP GET request, HTTP 200 OK response│
│                                                │
│  ② 消息语法 ──→ 字段怎么排？怎么分隔？           │
│     e.g., HTTP: method sp URL sp version cr lf  │
│                                                │
│  ③ 消息语义 ──→ 每个字段是什么意思？             │
│     e.g., 301 = "你找的东西搬家了"               │
│                                                │
│  ④ 通信规则 ──→ 什么时候发？什么时候回？         │
│     e.g., 服务器必须先收到请求才能发响应         │
└────────────────────────────────────────────────┘

开放协议 (RFC 公开)    vs    私有协议
HTTP, SMTP, DNS             Skype, Zoom (自定协议)
任何人都能实现              只有自己能用
```

### 卡片 2.1.5：TCP vs UDP —— 传输层给应用层的「服务菜单」

```
         TCP 提供的服务              UDP 提供的服务
    ┌────────────────────┐    ┌────────────────────┐
    │ ✅ 可靠传输         │    │ 只有：              │
    │    (不丢、不错、不重)│    │ 进程到进程的数据传送  │
    │ ✅ 流量控制         │    │ (多路复用/分解)     │
    │    发送方不会淹没    │    │                    │
    │    接收方缓冲区      │    │ ❌ 不保证可靠       │
    │ ✅ 拥塞控制         │    │ ❌ 不保证有序       │
    │    网络堵了就减速    │    │ ❌ 不保证不重复     │
    │ ✅ 面向连接          │    │ ❌ 没有流量控制    │
    │    通信前先握手       │    │ ❌ 没有拥塞控制    │
    │                    │    │                    │
    │ ❌ 不保证时序        │    │                    │
    │ ❌ 不保证最小带宽    │    │                    │
    └────────────────────┘    └────────────────────┘

❓ 为什么还要 UDP？
  ① 没有连接建立的延迟（一次RTT）
  ② 没有连接状态（服务器能支持更多客户端）
  ③ 头部开销小（TCP 20字节 vs UDP 8字节）
  ④ 应用层可以自己控制发送速率（不用被拥塞控制限制）

实际用途：DNS 查询、实时音视频、在线游戏、IoT 传感器数据
```

```
                               │  IP      │

  ✅ 加密（没人能偷看）
```

### 卡片 2.1.7：TCP Socket 编程流程

```
      Server (服务端)                    Client (客户端)
  ┌─────────────────────┐          ┌─────────────────────┐
  │                     │          │                     │
  │  socket()           │          │  socket()           │
  │    ↓                │          │    ↓                │
  │  bind()  绑定端口    │          │  connect() 连接服务端│
  │    ↓                │          │    │                │
  │  listen() 开始监听  │          │    │   TCP三次握手    │
  │    ↓                │          │    │ ←─── 发生在OS   │
  │  accept() 等待连接  │ ◄══════  │    ↓                │
  │    ↓                │  连接建立 │  send() 发送数据    │
  │  recv() 接收数据    │ ◄══════  │    ↓                │
  │    ↓                │          │  recv() 接收响应    │
  │  send() 发送响应    │ ═══════► │    ↓                │
  │    ↓                │          │  close() 关闭连接   │
  │  close() 关闭连接   │          │                     │
  └─────────────────────┘          └─────────────────────┘

关键点：
  • accept() 返回一个新的 socket，专门服务这个客户端
  • 原来的 socket 继续监听新连接
  • 这就是为什么一个服务器能同时处理多个客户端
```

### 卡片 2.1.8：UDP Socket 编程流程

```
      Server (服务端)                    Client (客户端)
  ┌─────────────────────┐          ┌─────────────────────┐
  │                     │          │                     │
  │  socket(SOCK_DGRAM) │          │  socket(SOCK_DGRAM) │
  │    ↓                │          │    ↓                │
  │  bind()  绑定端口    │          │  (不需要 connect!)   │
  │    ↓                │          │    ↓                │
  │  recvfrom() 收数据  │ ◄══════  │  sendto() 发数据    │
  │  同时拿到发送方地址   │          │  附带目标IP+端口     │
  │    ↓                │          │    ↓                │
  │  sendto() 回数据    │ ═══════► │  recvfrom() 收响应  │
  │    ↓                │          │    ↓                │
  │  继续循环...        │          │  close()            │
  └─────────────────────┘          └─────────────────────┘

UDP vs TCP 编程差异：
  • UDP 没有 connect() —— 不需要建立连接
  • 每次 sendto() 都要指定目标地址
  • 接收方从 recvfrom() 拿到发送方的地址
  • 没有 accept() —— 一个 socket 服务所有客户端
```

## 🔬 动手实验

### 实验 1：在你本机运行一个 TCP 服务器和客户端

```python
# server.py —— 先开一个终端运行这个
from socket import *
s = socket(AF_INET, SOCK_STREAM)
s.bind(('', 12000))
s.listen(1)
print('服务器已启动，等待连接...')
while True:
    conn, addr = s.accept()
    print(f'收到来自 {addr} 的连接')
    msg = conn.recv(1024).decode()
    conn.send(msg.upper().encode())
    conn.close()
```

```python
# client.py —— 再开一个终端运行这个
from socket import *
c = socket(AF_INET, SOCK_STREAM)
c.connect(('localhost', 12000))
c.send('hello from chapter 2!'.encode())
reply = c.recv(1024).decode()
print(f'收到回复: {reply}')
c.close()
```

### 实验 2：看看你电脑上哪些进程在监听

```bash
# Windows
netstat -an | findstr LISTENING

# Linux/Mac
netstat -tlnp
# 或者
ss -tlnp
```

你会看到类似：
```
tcp  0  0  127.0.0.1:12000  0.0.0.0:*  LISTENING
```
这就是刚才你的 Python 服务器在 12000 端口等连接！
