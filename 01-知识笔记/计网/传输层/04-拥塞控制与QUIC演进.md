### 卡片 3.6.1：拥塞 vs 流量控制 —— 两个容易混淆的概念

```
  流量控制 (Flow Control):           拥塞控制 (Congestion Control):
  ┌──────────────────────────┐      ┌──────────────────────────┐
  │ 一个发送方 → 一个接收方    │      │ 很多发送方 → 网络         │
  │ 防止接收方缓冲区溢出       │      │ 防止网络拥塞（路由器缓冲区）│
  │ 手段: rwnd (接收窗口)     │      │ 手段: cwnd (拥塞窗口)    │
  │ 接收方告诉发送方          │      │ 发送方自己探测            │
  └──────────────────────────┘      └──────────────────────────┘

  实际发送窗口 = min(rwnd, cwnd)

  拥塞的表现：
    - 长延迟（路由器缓冲区排队越来越长）
    - 丢包（路由器缓冲区溢出）
  
  为什么是 top-10 问题：
    没有拥塞控制 → 大家都全速发送 → 网络崩溃 → 谁都发不了
    有了拥塞控制 → 各自减速 → 大家都还能通信
```

### 卡片 3.6.2：拥塞的三种场景 —— 越来越糟

```
场景 1：一个路由器，无限缓冲，两个流
  → 吞吐量可以接近 R/2，但延迟趋于无穷大
  → 代价：延迟！(排队论)

场景 2：一个路由器，有限缓冲，两个流
  → 丢包导致重传，重传占用带宽
  → 不必要重传 → 浪费的传输能力
  → 代价：有效吞吐量降低！

场景 3：四个发送方，多跳路径
  → 上游路由器转发了一个包，但下游路由器丢弃了它
  → 上游为该包消耗的带宽和缓冲全浪费了！
  → 代价：上游资源被浪费！

结论：拥塞控制的本质不是"避免丢包"，而是
      "不要发送已经注定会被丢弃的包"。
```

### 卡片 3.6.3：两种拥塞控制方法

```
端到端拥塞控制 (TCP 的方式):
  网络不给任何反馈
  发送方通过观察丢包和延迟来推断网络拥塞
  → TCP 的做法：丢包 = 拥塞信号

网络辅助拥塞控制:
  路由器直接告诉发送方"我拥塞了"
  方式：
    - 直接反馈：路由器发 choke packet 给发送方
    - 标记反馈：路由器在数据包上标记拥塞位
                (ECN: Explicit Congestion Notification)
                接收方看到标记后通过 ACK 通知发送方
```

### 卡片 3.6.4：AIMD —— 加性增、乘性减

```
AIMD = Additive Increase, Multiplicative Decrease
这是 TCP 拥塞控制的基础算法。

                                TCP 发送速率
                                    │
       ╱╲      ╱╲      ╱╲           │  锯齿形！
      ╱  ╲    ╱  ╲    ╱  ╲          │
     ╱    ╲  ╱    ╲  ╱    ╲         │  加性增：每个 RTT 线性增加 1 MSS
    ╱      ╲╱      ╲╱      ╲        │          (慢慢"探")
   ╱                              ╲  │
──╱────────────────────────────────╲─│── 时间
                                    │
  乘性减：丢包时速率砍半 (×0.5)
          大刀阔斧降下来，再慢慢升回去

为什么是 AIMD？
  已被证明：一种分布式的异步算法
  可以让全网流速率收敛到公平和高效！
  (Chiu & Jain 1989 的经典论文)
```

### 卡片 3.6.5：TCP 拥塞控制状态机

```
                  ┌──────────┐
                  │ 慢启动    │ ← 连接刚开始 / 超时后
                  │ Slow Start│   指数增长！每个 RTT 翻倍
                  └────┬─────┘
                       │ cwnd >= ssthresh
                       ▼
                  ┌──────────┐
                  │ 拥塞避免  │ ← 达到阈值后进入
                  │ CA       │   线性增长！每 RTT +1 MSS
                  └────┬─────┘
                       │ 收到 3 个重复 ACK
                       ▼
                  ┌──────────┐
                  │ 快速恢复  │ ← 不是超时，只是丢了一个段
                  │ Fast Rcv │   砍半 cwnd，线性增长
                  └────┬─────┘
                       │ 收到新 ACK
                       ▼
                  ┌──────────┐
                  │ 拥塞避免  │
                  └──────────┘

  超时 vs 3 个重复 ACK 的处理不同：
    超时 → 直接降到 cwnd=1, 重新慢启动 (Tahoe 做法)
    3 dup ACK → 砍半 cwnd, 进入快速恢复 (Reno 改进)
```

### 卡片 3.6.6：慢启动 —— 别一上来就全速

```
连接刚建立时，你不知道网络能承受多快。
一上来就全速发 → 直接堵塞网络 → 自找苦吃。

慢启动的策略：从 1 MSS 开始，指数增长！

  cwnd 初始 = 1 MSS

  RTT 1: 发 1 个段, 收到 1 个 ACK, cwnd = 2
  RTT 2: 发 2 个段, 收到 2 个 ACK, cwnd = 4
  RTT 3: 发 4 个段, 收到 4 个 ACK, cwnd = 8
  RTT 4: 发 8 个段, cwnd = 16
  ...

  为什么叫"慢"启动？
    看着快（指数增长），但比一上来就开大窗口"慢"。
    这个名字是历史遗留，实际上增长非常快！

  何时结束慢启动？
    - cwnd >= ssthresh → 进入拥塞避免
    - 发生丢包 → ssthresh = cwnd/2, cwnd = 1, 重新慢启动
```

### 卡片 3.6.7：快速重传 + 快速恢复

```
快速重传 (Fast Retransmit):
  收到 3 个重复 ACK → 不等到超时 → 立即重传丢掉的段！

  为什么是 3 个？
    1 个重复 ACK → 可能是乱序（后面的段跑前面来了）
    2 个重复 ACK → 更可能是乱序
    3 个重复 ACK → 几乎肯定是丢了！(概率非常高)

快速恢复 (Fast Recovery):
  收到 3 个重复 ACK 后的处理：
    ssthresh = cwnd / 2
    cwnd = ssthresh + 3 MSS  ← 砍半但不降到 1！(和超时不同)
    
  在快速恢复期间：
    每收到 1 个重复 ACK → cwnd += 1 MSS (可以继续发新段)
    收到新 ACK → 退出快速恢复, cwnd = ssthresh, 进入拥塞避免

  为什么要有快速恢复？
    收到重复 ACK 说明网络还能传包（只是丢了一个）
    → 不需要慢启动那么极端，砍半就够了
```

### 卡片 3.6.8：TCP CUBIC —— 比 Reno 更快恢复

```
TCP Reno 的问题：
  丢包后砍半，然后线性增长。
  在高带宽长延迟 (LFN) 链路上 → 恢复到全速要很久很久！

TCP CUBIC (Linux 默认, 也是大多数 Web 服务器用的):
  增长率是"三次函数" —— 离上次的 W_max 越远，增长越快
  离 W_max 越近，增长越慢（更谨慎）

  TCP 速率
    │
    │    W_max          CUBIC: 快速靠近 W_max
    │     ╱‾‾‾╲                    然后小心试探
    │    ╱      ╲                  
    │   ╱  CUBIC ╲     Reno: 一直在慢慢爬
    │  ╱          ╲────
    │ ╱   Reno     ╲
    │╱              ╲────────────
    └────────────────────────────── 时间

  CUBIC 的优势：
    - 更快恢复到上次的 W_max
    - 到达 W_max 后小心试探（三阶函数变平）
    - Linux 默认，你写的 Qt 程序在 Linux 上跑的就是 CUBIC
```

### 卡片 3.6.9：BBR —— 不等丢包，看延迟

```
传统 TCP (Reno/CUBIC) 的思路：
  "一直加速直到丢包 → 丢包就是拥塞 → 减速"
  代价：一定要丢包才能发现拥塞！

BBR (Bottleneck Bandwidth and Round-trip propagation time):
  "测量 RTT 最小值（RTT_min）和最大吞吐量
   RTT 开始增大 → 路由器开始排队 → 马上减速！"
  
  不等丢包！在丢包之前就感知到拥塞。

  Google BBR 的效果（Google 内部骨干网）：
    - 比 CUBIC 更高的吞吐量
    - 同时更低的延迟！（因为不会让路由器排长队）

  核心洞察：
    "保持端到端的管道刚好满，但不要太满"
    太满 → 路由器排队 → RTT 增大
    刚好满 → 最高吞吐量 + 最低延迟
```

### 卡片 3.6.10：QUIC —— TCP 的灵魂 + UDP 的身体

```
QUIC = Quick UDP Internet Connections
Google 设计的应用层协议，跑在 UDP 上。

为什么要再造轮子？

  TCP + TLS 的问题（HTTP/2 栈）：
    ① TCP 握手 + TLS 握手 = 2 个 RTT 才能开始发数据
    ② TCP 丢包 → 后面所有流都阻塞（TCP 队头阻塞）
    ③ TCP 在内核实现 → 升级协议要升级操作系统！
    ④ 移动网络切换（WiFi→4G）→ TCP 连接断开 → 重建！

  QUIC 的解决：
    ┌──────────────────────────────┐
    │ HTTP/2 over TCP              │  HTTP/3 over QUIC
    │                              │
    │ IP                           │  IP
    │ TCP (可靠 + 拥塞)             │  UDP (只管端口)
    │ TLS (加密 + 认证)             │  QUIC (可靠 + 拥塞 + 加密 + 多流)
    │ HTTP/2 (多路复用)             │  HTTP/2 (精简版)
    │                              │
    │ 握手: TCP(1RTT)+TLS(1RTT)    │  握手: 1 RTT (0-RTT 重连!)
    │ HOL: TCP 层面所有流一起卡    │  HOL: 每个流独立! 一个丢不影响其他
    └──────────────────────────────┘

  QUIC 的核心创新：
    ① 连接建立 = 可靠性 + 加密 + 认证 + 拥塞控制全在一个 RTT
    ② 多流复用但每个流独立可靠传输（一个丢包不影响其他流！）
    ③ 在用户态实现 → 升级 QUIC = 升级应用，不需要升级内核
    ④ Connection ID → 切换网络不掉线！

  你写的 Qt 程序如果做 HTTP 请求：
    现在：HTTP/1.1 或 HTTP/2 over TCP
    未来：HTTP/3 over QUIC over UDP
```
