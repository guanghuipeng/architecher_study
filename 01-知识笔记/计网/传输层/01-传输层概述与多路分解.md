### 卡片 3.1.1：传输层到底干什么？—— 最重要的心智模型

```
  ┌─────────────────────────────────────────────────────────┐
  │                                                         │
  │   网络层 (IP) 的承诺：                                    │
  │     "我帮你在主机之间传数据"                               │
  │     主机 A  ←──────────────→  主机 B                     │
  │                                                         │
  │   传输层 (TCP/UDP) 的承诺：                               │
  │     "我帮你在进程之间传数据"                               │
  │     进程 P1 (浏览器) ←────→ 进程 P2 (Web Server)          │
  │                                                         │
  │   关键差异：                                              │
  │     网络层 = 主机到主机 (host-to-host)                    │
  │     传输层 = 进程到进程 (process-to-process)              │
  │                                                         │
  └─────────────────────────────────────────────────────────┘

  一个类比（Kurose 的家信模型）：

    Ann 家有 12 个小孩                Bill 家有 12 个小孩
    ┌─────────────────┐              ┌─────────────────┐
    │ A1 A2 ... A12   │              │ B1 B2 ... B12   │
    └────────┬────────┘              └────────┬────────┘
             │                                │
        ┌────┴────┐                      ┌────┴────┐
        │  Ann    │  ← 传输层协议 ←→     │  Bill   │
        │ (收集信  │                      │ (分发信  │
        │  贴邮票) │                      │  给弟妹) │
        └────┬────┘                      └────┬────┘
             │                                │
        ┌────┴────────────────────────────────┴────┐
        │             邮政服务 (网络层)              │
        │          只管把信从A家送到B家              │
        │          不管信是谁写的、给谁的             │
        └──────────────────────────────────────────┘

    网络层 = 邮政系统：把信件从 Ann 家送到 Bill 家
    传输层 = Ann/Bill：Ann 收集弟妹的信、封装、交给邮政
                      Bill 收到信、拆封、分发给对应的弟妹
```

**关键洞察**：网络层不知道"进程"的存在。它只看 IP 地址。传输层加上 port number，才能区分同一台机器上的不同进程。

### 卡片 3.1.2：发送方和接收方各做什么

```
  发送方 (Sender) 的动作：
  ┌────────────────────────────────────┐
  │  应用层                              │
  │    │  app msg = "GET /index.html"   │
  │    ▼                                 │
  │  传输层                              │
  │    │  ① 把 app msg 切成 segment(s)   │
  │    │  ② 加上传输层头部 (port, seq#)   │
  │    │  ③ 交给网络层                    │
  │    ▼                                 │
  │  网络层                              │
  └────────────────────────────────────┘

  接收方 (Receiver) 的动作：
  ┌────────────────────────────────────┐
  │  网络层                              │
  │    │ 收到 IP datagram               │
  │    ▼                                 │
  │  传输层                              │
  │    │  ① 检查头部、校验和             │
  │    │  ② 重组 segments → app msg     │
  │    │  ③ 通过 socket 交给正确的进程   │
  │    ▼                                 │
  │  应用层                              │
  └────────────────────────────────────┘
```

### 卡片 3.1.3：TCP vs UDP —— 两张「服务菜单」对比

```
  ┌──────────────────────────────────┬──────────────────────────────┐
  │        TCP 服务                   │        UDP 服务              │
  ├──────────────────────────────────┼──────────────────────────────┤
  │ ✅ 可靠传输                       │ ❌ 不可靠                     │
  │    (数据不丢、不错、不乱序)         │    (发出去就不管了)            │
  │                                  │                              │
  │ ✅ 流量控制                       │ ❌ 没有流量控制                │
  │    (发送方不会淹没接收方缓冲区)     │    (接收方缓冲区可能溢出)       │
  │                                  │                              │
  │ ✅ 拥塞控制                       │ ❌ 没有拥塞控制                │
  │    (网络堵了就减速)                │    (可以全速发送)              │
  │                                  │                              │
  │ ✅ 面向连接                       │ ❌ 无连接                     │
  │    (通信前先三次握手)              │    (不需要握手，直接发)         │
  │                                  │                              │
  │ ❌ 不保证最小带宽                  │ ❌ 不保证最小带宽              │
  │ ❌ 不保证时延                     │ ❌ 不保证时延                  │
  └──────────────────────────────────┴──────────────────────────────┘

  TCP 是"可靠的字节流"（就像水管，流出来的是连续的、有序的字节）
  UDP 是"不可靠的数据报"（就像扔纸飞机，每张独立飞，可能丢了也可能到了）
```

### 卡片 3.1.4：为什么需要 UDP？—— 不是所有场景都要可靠

```
  上一章你学过：UDP 不保证可靠，为什么还要用？

  ① 没有连接建立的延迟（省了 1 个 RTT）
     DNS 查一个域名 → 发 UDP 包 → 收 UDP 响应 → 总共 1 RTT
     如果用 TCP → 三次握手 (1 RTT) + 查询 + 响应 (1 RTT) = 2 RTT

  ② 没有连接状态
     服务器不需要为每个客户端维护连接状态
     DNS 服务器每秒处理数万查询 → 用 TCP 早就爆了

  ③ 头部开销小
     TCP 头部：20 字节（不含选项）
     UDP 头部：8 字节

  ④ 应用层可以自己控制
     不用被 TCP 拥塞控制限制发送速率
     视频会议每秒要发 30 帧 → TCP 一丢包就降速 → 画面糊了
     UDP 丢几帧无所谓，但帧率不能降！

  实际用途：
    DNS 查询       → 快速、简短
    实时音视频      → 容忍丢包、不能等
    在线游戏       → 延迟 > 可靠性
    SNMP           → 网络管理
    HTTP/3 (QUIC)  → 在 UDP 上重建可靠性！
```

### 卡片 3.2.1：多路复用/分解 —— 怎么把段交给正确的 Socket？

```
  这是传输层最基础的功能，也是最容易忽略的

  ┌──────────────────────────────────────────────────┐
  │                                                  │
  │  多路复用 (Multiplexing) @ 发送方：               │
  │    从多个 socket 收数据 → 加传输层头部 → 交给网络层 │
  │                                                  │
  │  多路分解 (Demultiplexing) @ 接收方：              │
  │    从网络层收 segment → 看头部 → 交给正确的 socket  │
  │                                                  │
  └──────────────────────────────────────────────────┘

  图解：

    发送方 (主机 A)                    接收方 (主机 B)
  ┌──────────────────┐            ┌──────────────────┐
  │ P1  P2  P3  P4   │            │ P1  P2  P3  P4   │
  │ │   │   │   │    │            │ ▲   ▲   ▲   ▲    │
  │ ▼   ▼   ▼   ▼    │            │ │   │   │   │    │
  │ ┌─────────────┐  │            │ ┌─────────────┐  │
  │ │  传输层      │  │            │ │  传输层      │  │
  │ │  多路复用    │──┼────────────┼─│  多路分解    │  │
  │ └─────────────┘  │            │ └─────────────┘  │
  └──────────────────┘            └──────────────────┘
       Multiplexing                  Demultiplexing
```

### 卡片 3.2.2：UDP 怎么分解？—— 只看目的端口

```
  UDP socket 的标识 = (目的 IP, 目的 Port)

  ┌─────────────────────────────────────────────────┐
  │                                                 │
  │  UDP 的分解逻辑：                                │
  │   收到一个 UDP segment → 看 destination port #   │
  │   → 找到绑定这个 port 的 socket → 把数据交过去    │
  │                                                 │
  │  不管源 IP 是什么！不管源端口是什么！              │
  │                                                 │
  └─────────────────────────────────────────────────┘

  例子：
    serverSocket = socket(AF_INET, SOCK_DGRAM)
    serverSocket.bind(('', 6428))  ← 服务端绑定 6428

    来自 A:5775 → 目的 6428 ─┐
    来自 B:9157 → 目的 6428 ─┼─→ 全部进入同一个 socket!
    来自 C:3333 → 目的 6428 ─┘

  这就是为什么 UDP 服务器只有一个 socket 可以服务所有客户端！
  因为你不需要知道"是谁发的"——每个数据报独立，来了就收。
```

### 卡片 3.2.3：TCP 怎么分解？—— 必须用 4-tuple！

```
  TCP socket 的标识 = 4-tuple (源IP, 源Port, 目的IP, 目的Port)

  ┌──────────────────────────────────────────────────┐
  │                                                  │
  │  TCP 的分解逻辑：                                 │
  │   服务端有 listening socket (等连接)              │
  │   每个 accept() 生成一个新的 connected socket     │
  │   每个 connected socket 由 4-tuple 唯一标识       │
  │                                                  │
  └──────────────────────────────────────────────────┘

  例子：Web 服务器监听 80 端口

    服务器 IP = B, port = 80 (listening)

    客户端 A:5775 → B:80  →  4-tuple: (A, 5775, B, 80)  →  socket 1
    客户端 C:5775 → B:80  →  4-tuple: (C, 5775, B, 80)  →  socket 2 (源IP不同!)
    客户端 C:9157 → B:80  →  4-tuple: (C, 9157, B, 80)  →  socket 3 (同一台机器不同进程!)

  三个段，都是送到 B:80，但被分解到三个不同的 socket！
  因为 TCP 是"连接"的——每个连接是独立的会话。

  ═════════════════════════════════════════════════════

  UDP vs TCP 分解的本质区别：

    UDP: 一个 socket 服务所有人 (无连接 → 不需要区分)
    TCP: 一个 socket 服务一个连接 (有连接 → 必须一一对应)
```

### 卡片 3.3.1：UDP 段结构 —— 极简主义

```
  UDP 段格式（RFC 768）：

   0              16              32
   ┌──────────────┬──────────────┬──────────────────┐
   │ 源端口 #      │ 目的端口 #    │  长度             │
   │ (2 bytes)    │ (2 bytes)    │  (2 bytes)       │
   ├──────────────┴──────────────┼──────────────────┤
   │         校验和               │                   │
   │       (2 bytes)             │   应用层数据       │
   ├─────────────────────────────┤   (payload)       │
   │                             │                   │
   │       应用层数据             │                   │
   │       (payload)             │                   │
   └─────────────────────────────┴───────────────────┘

  就这么简单！4 个字段，8 字节头部：
    • 源端口：发送方端口号（可选，不需要回复时可为 0）
    • 目的端口：接收方端口号（必须的，用于分解）
    • 长度：整个 UDP 段的字节数（含头部）
    • 校验和：检测错误（含头部+数据+IP 伪首部）

  对比：TCP 头部至少 20 字节，UDP 只要 8 字节

  ════════════════════════════════════════════════════

  UDP 发送方动作（极简）：
    ① 应用层给一段数据
    ② 填上源端口、目的端口
    ③ 计算校验和
    ④ 交给 IP 层 → 发出去
    ⑤ 忘了它！（不发 ACK，不重传，不管了）

  UDP 接收方动作（极简）：
    ① 从 IP 层收到 UDP segment
    ② 检查校验和（可选）
    ③ 看目的端口 → 交给对应的 socket
    ④ 没有第④步了！
```

### 卡片 3.3.2：UDP 校验和 —— 怎么检测传输错误

```
  校验和的目标：检测 UDP segment 中的 bit 翻转错误

  算法：将数据按 16-bit 分组，求反码和 (one's complement sum)

  发送方计算：
    ① 把 UDP segment 分成 16-bit 的字
    ② 把所有字相加（有进位则回卷）
    ③ 对和取反码 → 放入 UDP 校验和字段

  接收方验证：
    ① 对收到的 segment 做同样的加法（包括校验和字段）
    ② 如果结果是全 1 (0xFFFF) → 无错误
    ③ 否则 → 检测到错误

  一个简单例子：
    发送的是: 5, 6 → 和 = 11 → 校验和 = ~11

    传输正确：
      收到的: 4, 6, ~~= 4+6+~~ = 10
      → 4+6+~~ = 10 ≠ 全1 → 等等不对...

    让我用二进制演示：

    字1:    0110011001100110
    字2:    0101010101010101
    ────────────────────────
    和:     1011101110111011
    校验和:  0100010001000100  (对和取反码)

    接收方验证：
    字1+字2+校验和 = 1011101110111011 + 0100010001000100 = 1111111111111111 ✅
                                                              ^^^^^^^全1 = 无错误

  ⚠ 重要：UDP 校验和是可选的！
    发送方可以选择不计算（填 0），接收方可以选择不验证
    但 IPv6 强制要求 UDP 校验和
```

### 卡片 3.3.3：UDP 校验和 —— 为什么弱？

```
  ┌─────────────────────────────────────────────┐
  │  校验和的弱点：某些多位错误检测不出来！       │
  │                                             │
  │  字1:    0110011001100110                    │
  │  字2:    0101010101010101                    │
  │  和:     1011101110111011                    │
  │  校验和:  0100010001000100                    │
  │                                             │
  │  如果两个字的同一位同时翻转：                   │
  │  字1':   0010011001100110 (第2位翻转)         │
  │  字2':   0001010101010101 (第2位也翻转)       │
  │  和':    0011101110111011                     │
  │  校验和': 1100010001000100                     │
  │                                             │
  │  接收方验证：                                 │
  │  字1'+字2'+校验和 =  竟然也可能是全1!          │
  │  → 两个对称的错误可能互相抵消！               │
  └─────────────────────────────────────────────┘

  这就是为什么需要更强的校验：
    链路层 (CRC): 检测能力更强
    TLS (MAC):   防止篡改和检测错误
    TCP:        同样的校验和算法，但 TCP 有重传机制兜底

  Kurose 幻灯片原话："Even though numbers have changed (bit flips),
  no change in checksum!" ← 这是故意设计的吗？不是，是穷方案（1970年代计算便宜）
```

### 实验 2：Python 演示 UDP 多路分解

```python
# 在一个终端运行 —— UDP server
from socket import *
s = socket(AF_INET, SOCK_DGRAM)
s.bind(('', 9999))
print("UDP server on port 9999")
while True:
    data, addr = s.recvfrom(1024)
    print(f"Got '{data.decode()}' from {addr}")
    s.sendto(f"Echo: {data.decode()}".encode(), addr)
```

```bash
# 在另一个终端 —— 两个客户端用不同源端口，但发到同一目的端口
```

## ❓ 思考题

> **Q1: 为什么 TCP 用 4-tuple 而 UDP 只用目的端口来分解？**
>
> <details>
> <summary>点击查看答案</summary>
>
> 因为 TCP 是面向连接的。每个客户端连接是独立的会话——有自己的序号空间、自己的缓冲区、自己的拥塞状态。所以必须精确区分每个连接。
>
> UDP 是无连接的——每个数据报独立，没有"会话"的概念。收到一个数据报，根据目的端口投递给对应的进程就完了，不需要知道是谁发来的。
> </details>

> **Q2: 你在第二章写过 TCP server 代码——什么时候 accept() 会返回？accept() 返回的 socket 和原来的 listening socket 有什么不同？**
>
> <details>
> <summary>点击查看答案</summary>
>
> accept() 在三次握手完成后返回。返回的新 socket 是一个 connected socket，由 4-tuple 唯一标识，专门服务这一个客户端。原来的 listening socket 继续接受新连接。
>
> listening socket 只用 2-tuple (目的IP, 目的Port) 标识，connected socket 用 4-tuple 标识。
> </details>

> **Q3: 你的 Qt 项目中什么时候会选 TCP？什么时候会选 UDP？**
>
> <details>
> <summary>点击查看答案</summary>
>
> TCP: 数据库连接、HTTP API 调用、文件传输、命令下发（需要可靠）
> UDP: 实时日志上报、心跳包、视频推流、局域网设备发现（容忍丢失、追求低延迟）
> </details>
