### 卡片 3.4.1：可靠传输的五味药

```
不管你用 rdt3.0、GBN、SR 还是 TCP，可靠传输就靠这五个机制：

┌─────────────────────────────────────────────────────────┐
│                                                         │
│  ① 校验和 (Checksum)    → 检测 bit 错误                  │
│  ② 序号 (Sequence #)    → 检测重复包 / 乱序              │
│  ③ ACK (确认)           → 告诉对方"我收到了"             │
│  ④ 定时器 (Timer)       → 检测丢包                       │
│  ⑤ 重传 (Retransmit)    → 丢了就再发                     │
│                                                         │
│  五味齐全 → 不可靠信道 → 可靠传输                         │
│  少一味 → 协议有漏洞                                     │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 卡片 3.4.2：rdt 演进七步走

```
rdt1.0  ─→  rdt2.0  ─→  rdt2.1  ─→  rdt2.2  ─→  rdt3.0  ─→  流水线  ─→  GBN/SR
  │           │           │           │           │
  │           │           │           │           │
  ▼           ▼           ▼           ▼           ▼
信道完美    信道出错      ACK/NAK     扔掉 NAK     信道丢包
啥也不做    +校验和      也会出错     用重复 ACK    +定时器
           +ACK/NAK     +序号(0/1)   替代 NAK     所有机制
           致命漏洞:    解决坏ACK/    TCP用的      齐聚！
           ACK/NAK      NAK不确定    就是这思路
           也会出错！

每个版本只在上一版基础上加一个机制。没有跳跃。
```

### 卡片 3.4.3：rdt2.0 的致命漏洞

```
rdt2.0 加了校验和 + ACK/NAK，逻辑看起来完整 ——
但 ACK/NAK 自己也会在不可靠信道上出错！

  发送方                           接收方
    │── pkt0 ───────────────────►│  正确收到！发 ACK
    │◄── ACK（损坏！分不清是ACK还是NAK）──│
    │
    │  "如果我不重传，万一是 NAK 呢？数据丢了"
    │  "如果我重传，万一是 ACK 呢？接收方收到重复包"
    │
    ▼
  解决：加序号。接收方能识别"这是重传的重复包"。
  因为 Stop-and-Wait 同时只有一个包在飞 → 0/1 两个序号就够！
```

### 卡片 3.4.4：序号 —— 为什么 0 和 1 就够

```
Stop-and-Wait 协议中，发送方同一时刻只有一个包在飞。
接收方只需要区分两种情况：
  - 这是新包（和上一个不同）
  - 这是重传的旧包（和上一个相同）

两个序号就够了。

  发送方视角：            接收方视角：
    发 pkt0, 等 ACK0         期望 seq=0
    收到 ACK0 → 发 pkt1     收到 pkt0 → 交上层, 期望 seq=1
    收到坏包 → 重发 pkt0     又收到 pkt0 → 重复！扔掉, 重发 ACK0
    发 pkt1, 等 ACK1         收到 pkt1 → 交上层, 期望 seq=0
    ...                      ...

但流水线协议（GBN/SR）有 N 个包同时在飞 → 需要更大序号空间！
```

### 卡片 3.4.5：rdt2.2 —— NAK-free 设计（TCP 用的就是这个）

```
rdt2.1: ACK 和 NAK 两种反馈
rdt2.2: 只用 ACK，NAK 用"重复 ACK"替代

  场景：接收方期望 seq=0，但收到坏包
  rdt2.1: 发 NAK → 发送方重传
  rdt2.2: 发 ACK1（上一个正确收到的包的 ACK）→ 发送方看到 ACK1 而不是期望的 ACK0
           → 知道出问题了 → 重传

  效果完全一样，但少了一种消息类型。
  这就是 TCP "重复 ACK 触发快速重传" 的思想来源！
```

### 卡片 3.4.6：rdt3.0 —— 定时器是统一的兜底机制

```
rdt3.0 在 rdt2.2 基础上加了定时器处理丢包。
它的设计哲学很重要：

  "收到坏 ACK？忽略。收到 NAK？忽略。收到序号不对的 ACK？忽略。
   所有这些问题，统一靠定时器超时来兜底。"

为什么？
  收到坏包 → 不知道它原本是什么 → 重传可能浪费 → 不如等超时
  收到错误序号 → 可能是迟到的 ACK → 不说明任何问题 → 忽略

定时器是最后的安全网。不管什么出了问题 —— 超时 → 重传。
```

### 卡片 3.4.7：Stop-and-Wait 的性能悲剧

```
1 Gbps 链路, 15ms 传播延迟, 8000 bit 数据包:

  传输时间 D_trans = 8000 / 10^9 = 8 微秒
  RTT = 2 × 15ms = 30ms = 30000 微秒

  利用率 U = D_trans / (D_trans + RTT)
           = 8 / 30008
           ≈ 0.027%

  也就是：99.97% 的时间在等 ACK！

  就像一辆高铁，每次只运一个包裹，
  运完必须等对方签收回执。
  高铁再快也没用 —— 时间全花在等回执上。
```

### 卡片 3.4.8：流水线 (Pipelining) —— 不等 ACK，连续发

```
Stop-and-Wait:
  发送方:  ████░░░░░░░░░░░░░░░░░░░░████░░░░░░░░░░░░
            pkt0    等 ACK...        pkt1   等 ACK...

流水线 (3个包在飞):
  发送方:  ████████████████████████████░░░░░░░░░░
            pkt0  pkt1  pkt2        等 ACK...

利用率直接 × N！

代价：需要更大的序号空间 + 需要缓冲（发送方或接收方）
```

### 卡片 3.4.9：Go-Back-N vs Selective Repeat

```
                     GBN                          SR
  ┌─────────────────────────────────────────────────────────┐
  │ ACK 类型      累积 ACK                   逐个 ACK        │
  │               ACK(n) 确认 n 及之前全部   每个包单独 ACK   │
  │                                                         │
  │ 定时器        1 个（最老的未 ACK 包）    每个包 1 个      │
  │                                                         │
  │ 丢包时重传    从丢的包开始全部重发       只重传丢的那个    │
  │               (Go Back N 步!)                            │
  │                                                         │
  │ 乱序包        扔掉！                    缓冲起来          │
  │                                                         │
  │ 接收方缓冲    不需要                    需要              │
  │                                                         │
  │ 实现复杂度    低                        高               │
  └─────────────────────────────────────────────────────────┘

GBN 适合: 出错率低的信道（大部分时候不丢包，重传少）
SR 适合:  出错率高的信道（频繁丢包时避免大量无效重传）

TCP 混合两者！
```

### 卡片 3.4.10：SR 的序列号陷阱

```
SR 有一个隐蔽的 bug：

序号空间 = {0, 1, 2, 3}（4 个序号，循环使用）
窗口大小 N = 3

场景 A（正常）:
  发送方发 pkt0, pkt1, pkt2 → 接收方全部收到 → 全部 ACK → 窗口滑动
  [OK]

场景 B（灾难）:
  发送方发 pkt0, pkt1, pkt2 → 接收方全部收到 → 但 ACK 全部丢失！
  发送方超时重传 pkt0 → 接收方看到 seq=0...
  "这个 0 是新的还是旧的重传？分不清！"
  
  因为窗口 N=3 > 序号空间/2 = 2，新旧序号重叠了。

解决：窗口大小 ≤ 序号空间的一半
  4 个序号 → 窗口最多 2
  这个约束保证了新旧区间绝不重叠。
```
