### 卡片 3.5.1：TCP 的十个特性 —— 一句话概括

```
TCP 是什么？

  "点对点、面向连接、全双工、可靠有序的字节流、
   带流量控制和拥塞控制的传输层协议。"

  点对点              → 一个发送方，一个接收方（不能广播）
  面向连接             → 通信前必须三次握手
  全双工               → 数据可以同时双向流动
  可靠有序             → 不丢、不错、不乱序
  字节流               → 没有"消息边界"（和 UDP 的数据报不同）
  流量控制             → 发送方不会淹没接收方缓冲区
  拥塞控制             → 发送方不会淹没网络
  流水线               → 多个段同时在飞（累积 ACK）
  MSS (最大段大小)     → 一般是 1460 字节（以太网 MTU 1500 - IP头20 - TCP头20）
```

### 卡片 3.5.2：TCP 段结构 —— 每个字段都要认识

```
  0              4              8                             16              24              32
 ┌──────────────┬──────────────┬──────────────────────────────┬──────────────┬──────────────┐
 │  源端口 #     │  目的端口 #   │                              │              │              │
 │ (16 bits)    │ (16 bits)    │       序号 (32 bits)          │   确认号      │              │
 ├──────────────┴──────────────┤                              │ (32 bits)    │              │
 │                             │                              │              │   接收窗口    │
 │                             ├──────────────────────────────┴──────────────┤  (16 bits)   │
 │                             │  头长度  │ 保留 │ U A P R S F │              │              │
 │                             │ (4 bits) │(6bit)│ R C S S Y I │   接收窗口    │              │
 │                             │          │      │ G K H T N │  (16 bits)    │              │
 ├─────────────────────────────┼──────────┼──────┴───────────┴──────────────┴──────────────┤
 │         校验和 (16 bits)     │      紧急数据指针 (16 bits)                              │
 ├─────────────────────────────┴─────────────────────────────────────────────────────────┤
 │                            选项 (可变长度, 最大 40 字节)                                 │
 ├───────────────────────────────────────────────────────────────────────────────────────┤
 │                            应用层数据 (可变长度)                                        │
 └───────────────────────────────────────────────────────────────────────────────────────┘

 关键字段解释：

  序号 (Sequence Number)：    不是"第几个段"，而是"本段数据的第一个字节在字节流中的编号"
  确认号 (ACK Number)：       期望收到的下一个字节的序号（累积确认）
  ACK 标志位：                确认号字段有效
  SYN 标志位：                建立连接
  FIN 标志位：                关闭连接
  RST 标志位：                复位连接
  接收窗口 (rwnd)：           接收方还能收多少字节（流量控制）
  校验和：                    和 UDP 同样的算法
```

### 卡片 3.5.3：TCP 序号 —— 按字节编号，不是按段编号！

```
这是最容易搞混的地方！

  Host A 要发 500,000 字节的文件, MSS = 1000 字节
  第一个段的 seq # = 0
  第二个段的 seq # = 1000  (不是 1！是按字节数！)
  第三个段的 seq # = 2000

  ┌──────────┬──────────┬──────────┬─────┐
  │ 0...999  │1000..1999│2000..2999│ ... │  ← 字节流
  └──────────┴──────────┴──────────┴─────┘
   段1:seq=0  段2:seq=1000 段3:seq=2000

  ACK 也是按字节的：
   收到段1 (0..999) → ACK=1000 ("期望下一个字节是 1000")
   收到段2 (1000..1999) → ACK=2000
   
  Telnet 例子 (你敲一个字符 'C'):
   Host A: Seq=42, ACK=79, data='C'
   Host B: Seq=79, ACK=43, data='C' (echo 回来)
   Host A: Seq=43, ACK=80
```

### 卡片 3.5.4：RTT 估计 —— 指数加权移动平均 (EWMA)

```
Q: 定时器设多长？
   太短 → 提前超时 → 不必要重传
   太长 → 包丢了半天才发现 → 浪费时间

A: 动态估计 RTT，加安全边界。

  EstimatedRTT = (1 - α) × EstimatedRTT + α × SampleRTT

  典型 α = 0.125

  这是指数加权移动平均 —— 越新的样本权重越大，
  越旧的样本指数衰减。

  还需要考虑 RTT 的波动：
  DevRTT = (1 - β) × DevRTT + β × |SampleRTT - EstimatedRTT|
  典型 β = 0.25

  超时间隔：
  TimeoutInterval = EstimatedRTT + 4 × DevRTT
                    └── 估计值 ──┘   └── 安全边界 ──┘

  这样 RTT 波动大时自动放宽超时间隔，稳定时收紧。
```

### 卡片 3.5.5：TCP 可靠传输 —— RDT 五味药怎么用

```
TCP 的可靠数据传输：

  校验和        → 和 UDP 相同算法
  序号          → 按字节编号（不是按段！）
  累积 ACK      → 和 GBN 一样
  一个定时器    → 和 GBN 一样（最老的未 ACK 字节）
  快速重传      → 收到 3 个重复 ACK → 不等超时，立即重传！
                 （这是 SR 的思想 —— 只重传丢的那个段）

  接收方处理乱序段：
    TCP 规范没说必须怎么做 —— 实现者自己决定
    可以缓冲（像 SR），也可以丢弃（像 GBN）
    实际上：现代 TCP 实现都会缓冲乱序段

  快速重传的巧妙之处：
    收到 ACK=100, ACK=100, ACK=100, ACK=100...
    → 说明接收方一直期待 seq=100 但收不到
    → seq=100 的段很可能丢了！
    → 不等超时，立即重传 seq=100
```

### 卡片 3.5.6：TCP 流量控制 —— 接收窗口 (rwnd)

```
流量控制 ≠ 拥塞控制！

  流量控制：防止发送方淹没接收方的缓冲区
            （发送方太快 vs 接收方处理太慢）

  拥塞控制：防止发送方淹没网络
            （太多发送方 vs 网络带宽不够）

  流量控制机制：

  接收方在 TCP 头里告诉发送方 rwnd (接收窗口):
    "我还能收 rwnd 个字节，别发太多！"

  发送方限制未 ACK 的数据量 ≤ rwnd:
    LastByteSent - LastByteAcked ≤ rwnd

  ┌────────────────────┐
  │  接收方缓冲区       │
  │ ┌──────────────┐   │
  │ │ 已交付上层    │   │
  │ ├──────────────┤   │  rwnd = 空闲空间
  │ │ 已收到未交付  │   │
  │ ├──────────────┤   │
  │ │   空  闲     │←──│ rwnd 字段
  │ │              │   │
  │ └──────────────┘   │
  └────────────────────┘

  如果 rwnd = 0 → 发送方停止发送！
  （但仍然可以发探测段，防止 rwnd 更新丢失导致死锁）
```

### 卡片 3.5.7：连接管理 —— 为什么必须三次握手？

```
两次握手为什么不够？三个场景证明它不行：

  场景 1：半开连接
    Client 发 SYN(x) → 延迟 → Client 超时断开
    → Server 收到延迟的 SYN, 回 SYNACK, 进入 ESTABLISHED
    → 但 Client 早就不在了！
    → Server 的资源被浪费

  场景 2：重复数据被接受
    Client 发 SYN(x) → Server ACK → 连接建立 → 传数据 → 关闭
    → 旧的 SYN(x) 在网络中延迟后到达 Server
    → Server 以为是新连接, 进入 ESTABLISHED
    → Client 发来的数据（其实是上一个连接的数据）被当成新连接数据！

  场景 3：Server 不知道 Client 是否 Alive
    两次握手后 Client 直接发数据
    → 如果 Client 发的 SYN 是旧的（延迟到达）
    → Server 分配资源 → Client 并不知道这个连接
    → 资源泄露

三次握手如何解决：
  Client → SYN(x)
  Server → SYNACK(y, ACK=x+1)  ← Server 确认收到 Client 的 SYN
  Client → ACK(y+1)             ← Client 确认收到 Server 的 SYNACK
                                  双向确认！没有歧义！
```

### 卡片 3.5.8：三次握手状态图

```
  Client                                    Server
  CLOSED                                    CLOSED
    │                                         │
    │ socket() + connect()                    │ socket() + bind() + listen()
    ▼                                         ▼
  SYN_SENT ──── SYN(seq=x) ──────────────► LISTEN
                ─── SYN(seq=x) ───────►       │
                                             │ 收到 SYN
                                             ▼
              ◄─── SYNACK(seq=y, ACK=x+1) ─ SYN_RCVD
                ◄── SYNACK(seq=y, ACK=x+1) ── │
    │                                         │
    │ 收到 SYNACK, 发 ACK                      │
    ▼                                         │ 收到 ACK
  ESTABLISHED ─── ACK(ACK=y+1) ──────────► ESTABLISHED
    │                                         │
    │ 开始发数据                               │ 开始发数据

注意：第二次握手时 Server 已经分配了资源（SYN_RCVD 状态）
     这就是 SYN Flood 攻击的原理 —— 大量伪造 SYN 让 Server 耗尽资源
     SYN Cookie 是防御手段（不在 SYN_RCVD 分配资源）
```

### 卡片 3.5.9：四次挥手 —— 为什么比握手多一次？

```
三次握手（建连接）→ 两次就够通信（SYN + SYNACK + ACK）

但关闭连接需要四次——为什么？

因为 TCP 是全双工的！每个方向必须独立关闭。

  Client                                    Server
  ESTABLISHED                               ESTABLISHED
    │                                         │
    │ close()                                 │
    ▼                                         │
  FIN_WAIT_1 ── FIN(seq=u) ──────────────►    │
                ── FIN(seq=u) ───────►        │ 收到 FIN
    │                                         ▼
    │                                    CLOSE_WAIT
    │         ◄── ACK(ACK=u+1) ────────────   │
    │         ◄── ACK(ACK=u+1) ───             │ (可能还有数据要发)
    ▼                                         │
  FIN_WAIT_2                                  │
    │                                         │ close()
    │                                         ▼
    │                                    LAST_ACK
    │         ◄── FIN(seq=v) ───────────────  │
    │         ◄── FIN(seq=v) ───               │
    ▼                                         │
  TIME_WAIT ── ACK(ACK=v+1) ─────────────► CLOSED
    │                                         │
    │ 等 2MSL...                              │
    ▼                                         │
  CLOSED

为什么比握手多一次？
  FIN_WAIT_1 → FIN_WAIT_2: 需要等 Server 确认 FIN（一次）
  FIN_WAIT_2 → TIME_WAIT:  需要等 Server 发自己的 FIN（再一次）
  Server 收到 FIN 后可能还有数据要发 → 不能立即回 FIN
  
  四次 = SYN + SYNACK(合并) vs FIN + ACK + FIN(不合并) + ACK
```

### 卡片 3.5.10：TIME_WAIT —— 为什么等 2MSL？

```
TIME_WAIT 是主动关闭方在发完最后一个 ACK 后进入的状态。
持续时长：2 × MSL (Maximum Segment Lifetime, 通常 2 分钟)

为什么存在？两个原因：

  原因 1：最后一个 ACK 可能丢失
    Client 发 ACK → 丢失
    Server 没收到 ACK → 超时 → 重发 FIN
    如果 Client 已经 CLOSED → 收到 FIN 回 RST → Server 出错
    TIME_WAIT 期间 Client 还能重发 ACK！

  原因 2：旧连接的残余包必须消亡
    连接 (srcIP:srcPort, dstIP:dstPort) 关闭后，
    网络中可能还有这个连接的残余数据包在游荡。
    等 2MSL 确保这些残余包全部超时消亡，
    否则新的同名连接可能收到旧数据。

  典型 MSL = 30秒 ~ 2分钟 → TIME_WAIT = 1~4 分钟

  你写服务器代码时遇到 "Address already in use" 错误
  → 就是因为端口还在 TIME_WAIT 状态！
  → 设置 SO_REUSEADDR 可以允许重用
```

### 卡片 3.5.12：TCP 接收方 ACK 生成策略 (RFC 5681)

```
  事件                                       TCP 接收方动作
  ─────────────────────────────────────────────────────────────
  收到有序段，期望序号匹配                   延迟 ACK（等 500ms，
  且所有之前数据已 ACK                      期望能顺路带回去）

  收到有序段，期望序号匹配                   立即发累积 ACK
  且之前有 ACK 在等待                       （合并确认两个段）

  收到乱序段（序号高于期望）                 立即发重复 ACK
  检测到缺口                                （告知发送方缺哪个）

  收到段填补了缺口                          立即发 ACK
  （从低端开始填补）                        （确认连续收到的部分）
```
